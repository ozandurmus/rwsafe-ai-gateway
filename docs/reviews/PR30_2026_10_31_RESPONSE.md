## D-01 (P1): a draft started before a withdrawal could bring the scope back with one approval

Fixed. `PolicyRegistryStore.withdrawScope` now supersedes, in the withdrawal's own transaction, every pending version of
the same rule, mode and scope key (with whatever approvals it holds), as `retirePlatform` does for a platform (PR 21
D-01). Pending drafts of other scopes and other modes keep waiting. The withdrawal time is the transaction's time
(`now()`), so the trigger can tell this withdrawal from an older one.

The V9 guard (`rwsafe_policy_rule_version_guard`, still unmerged, so edited in place) allows `pending -> superseded`
only when one of these holds:
- a newer version of the same rule, mode and scope key exists;
- a version of the same rule, mode and scope key was withdrawn in the same transaction (`withdrawn_at = now()`);
- the rule's platform is retired;
- the row is a V3 withdrawal request.

The review's correction 2 also tightened the newer-draft case to the draft's own mode and scope. The store only ever
supersedes within one mode and scope, so nothing else needed to change. One part of correction 2 was narrowed: the
review's `r.status = 'withdrawn'` would let any later direct SQL supersede a draft of a scope withdrawn long ago. The
guard therefore accepts only a withdrawal made in the same transaction.

Tests (`PolicyRegistryStoreTest`):
- `aDraftStartedBeforeAWithdrawalCanNeverBringTheScopeBack`:
  - a draft of the withdrawn scope that already holds the `security_admin` approval is superseded by the withdrawal, and the supersede is ledgered under `policy.scope_withdraw`;
  - the privacy officer's approval is then refused with `POLICY_NOT_PENDING`, and the scope stays withdrawn;
  - a draft made after the withdrawal cannot be superseded by direct SQL, either through an older withdrawal or through a newer draft of another scope (`POLICY_NO_REPLACEMENT`).
- `aWithdrawalLeavesOtherScopesAndTheirDraftsAlone`: drafts of another scope and of another mode stay pending, and one of them activates normally.
