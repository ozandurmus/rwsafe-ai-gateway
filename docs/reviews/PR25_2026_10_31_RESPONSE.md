## Questions for the Product Owner

| Question | Answer |
|---|---|
| Q-1 (storage model vs. ADR-009 §1-§3) | Decision (orchestrator for the PO): "ADR-009 is ACCEPTED and binds; implement its storage model". **Done.** The text lives outside PostgreSQL in the capture store on its own volume (`RWSAFE_CAPTURE_STORE_DIR`, a PVC in the deploy later): content-defined chunks of 8-64 KiB (Gear rolling hash), each addressed by HMAC-SHA256 under a key derived from the capture key (a keyed address, so the column is no "does this text exist" oracle; plain SHA-256 of guessable text would be one), stored once and reference-counted by triggers, encrypted with AES-256-GCM under a data key of its own; files are named by a random chunk id. PostgreSQL holds only `capture_record` (metadata, wrapped record key, MAC), `capture_manifest` (record to ordered chunks), `capture_chunk` (address, wrapped data key, size, reference count), the byte counter `capture_store_usage`, the read ledger, the receipts and the key events (`SchemaMatchesMigrationsTest.noCaptureTableHoldsContent`). MAX_STORE_BYTES (80 GiB, `RWSAFE_CAPTURE_MAX_STORE_BYTES`) evicts the oldest records without a hold before new chunks are stored and in every maintenance run, with `STORE_CAP_EVICTED` receipts, ledgered and counted on Health (`theByteCapEvictsTheOldestRecords`, `CaptureStoreTest.theByteCapEvictsOldestFirst`). Deletion (§4): one path for retention, the cap and shredding: records and manifests deleted, unreferenced chunks deleted (their row held the only wrapped data key: crypto-shredding), files removed, a receipt written; every deleted row and receipt is an `audit_event` row, which the SIEM export (PR 23, merged into this branch) sends; `SiemRecords` now lets the row key of `capture_record` and `capture_chunk` deletions leave as written when it is a canonical UUID (the event id the SIEM can purge) and the receipt, read and key-event numbers as numbers, anything else pseudonymised (`SiemSchemaTest.rowKeysLeaveOnlyInAllowListedShapesOtherwisePseudonymised`, `RedactedCaptureIntegrationTest.theByteCapEvictsTheOldestRecords`). Deduplication: `aRepeatedTextIsStoredOnce`, `CaptureStoreTest.aRepeatedChunkIsStoredOnceAndCounted`, `ChunkerAndViewTest.chunksAreBoundedCoverTheInputAndRepeatAfterAnInsertion`. **Interpretation:** ADR-009 §2 says "per-record data key"; with deduplication a chunk is shared by records, so the data key is per chunk and the record binding is the per-record MAC key (D-04). **Gaps in this slice (ADR-009 items not implemented):** (a) §2 C5: no special-category detector exists yet, so "C3 is not persisted when a C5 flag fired" cannot fire; (b) §2 masking layers 4 (Turkish names) and 5 (free-text heuristics) at persistence: `TextMasker` is still `rwmask-v1-slice1`, the stored rule set says so; (c) §3 the cap is enforced by the control plane's maintenance job, not by a worker (the worker module is empty), and the data plane's breaker reads its own spool volume rather than a watermark pushed in the snapshot; (d) §4 legal hold placed and lifted by `privacy_officer` with a case id: the store and the ledger support it (`setLegalHold`), no API yet; DSAR erasure (same path) and §6 DSAR search: no API yet; restore-time replay of receipts (ADR-002 §5): not in this slice; (e) §5 the decrypted view's watermark, no-download and per-page view rows belong to the screen that opens a record, which does not exist yet. |
| Q-2 (reader roles vs. ADR-009 §5) | Decision: "MVP reader roles are security_admin and privacy_officer; bind the DSAR reason code to privacy_officer only." **Done.** `security_admin` and `privacy_officer` read with a reason code and a case id; `DSAR` by anyone without `privacy_officer` is refused 403 `REASON_NOT_PERMITTED_FOR_ROLE` and ledgered `REFUSED_ROLE`. Recorded in `CURRENT_STATE.md`. Test: `contentLivesSealedOnTheStoreVolumeAndIsReadOnlyWithARoleAReasonAndACase`. |
| Q-3 (rotation vs. hold and retention) | Decision: "planned key rotation re-wraps the data keys of records that are still within retention or on legal hold under the new active key (a job, ledgered); emergency crypto-shredding (removing a key without re-wrap) stays possible and is a separate documented, ledgered operation." **Done.** Planned rotation: a new key and `active` pointing at it; the maintenance job re-wraps every record key of a record within retention or on hold, and every referenced chunk key, under the active key without decrypting content, in ledgered transactions with one `REWRAP` key event per previous key; Health shows what is still under older keys, and the old key is removed only when that is zero. Emergency shredding: the key id is added to the Secret's `shredded` list (and its file removed); the key is never used again and the job deletes every record under it or using a chunk under it with a `KEY_SHREDDED` receipt and an `EMERGENCY_SHRED` key event; a held record stays, unreadable, and is counted. A key that is merely missing (not listed) deletes nothing, so an accidental unmount cannot destroy data. Documented in `docs/operations/LOCAL_RUN.md` "Redacted capture". Tests: `plannedRotationRewrapsAndAnEmergencyShredDeletes`, `CaptureStoreTest.plannedRotationRewrapsAndEmergencyShreddingIsAKeyEvent`, `CaptureKeyringTest.plannedRotationRewrapsAndTheShreddedListDestroysAKey`. |
