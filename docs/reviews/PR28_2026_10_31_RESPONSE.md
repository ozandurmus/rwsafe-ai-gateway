# PR 28 second review: response

Review: `docs/reviews/PR28_2026_10_31_ARGON_ADMIN_UI_SLICE3.md` (Argon, MERGE WITH CORRECTIONS). The orchestrator's
decisions on the review's questions and findings are quoted per item; no further review round was asked for.

## Questions for the Product Owner

**Q-1 (reason codes per role).** Decision: "follow ADR-009 §5: security_admin may use the incident reason codes only;
privacy_officer may use DSAR only (a person holding both roles sees both sets). Enforce it on the server
(CaptureReadController) and mirror it in the UI; the drift test covers the mapping; ledger refusals as today."

Done. `CaptureReadController.REASONS_BY_ROLE` maps `security_admin` to `INCIDENT_INVESTIGATION`,
`FALSE_POSITIVE_REVIEW`, `LEGAL_HOLD_REVIEW`, `REGULATOR_REQUEST` and `privacy_officer` to `DSAR`; `REASONS` is their
union; a reader may give the union over its roles. A code outside it is refused 403 `REASON_NOT_PERMITTED_FOR_ROLE` and
ledgered `REFUSED_ROLE` with the reason and the case id, as before. The UI's `CAPTURE_REASONS_BY_ROLE` mirrors the map;
`CaptureReasonCodesUiTest` compares both lists and the mapping and checks the union for a person holding both roles.
Interpretation to confirm: "incident reason codes" is read as every non-DSAR code. The narrower reading (only
`INCIDENT_INVESTIGATION` and `FALSE_POSITIVE_REVIEW`) would leave `LEGAL_HOLD_REVIEW` and `REGULATOR_REQUEST` with no role
that may give them. ADR-009 §5 still names `security_analyst`, a role that does not exist yet; the records give the
incident read to `security_admin` (PR 25 Q-2). The ADR text is left to the architect.

**Q-2 (case id needs a letter).** Decision, with D-01: "a case id must contain at least one letter, and pass the shared
IdentifierCheck on the server (no identifier shapes, no 6+ digit runs); the UI mirrors the shape rules and never echoes a
refused value."

Done. `CaptureReadController.caseIdShape` requires 3 to 64 ASCII letters, digits, `_` or `-`, at least one letter, and
no `IdentifierCheck.identifierShape` hit (Tier-1 detectors on the value and its folded forms, six or more digits in a
row even across a separator); `IdentifierCheck.carriesIdentifier` then adds the estate-dictionary check (503
`MASKING_UNAVAILABLE` without the dictionary, ledgered first). The review's suggested `^TR\d{24}$` rule is covered by the
digit-run rule and the IBAN detector. Consequence: grouped numbers such as `CASE-2026-0001` are now refused (eight digits
joined across the hyphen); the tests and `LOCAL_RUN.md` use ids such as `CASE-A-0001`.

## Findings

**D-01 (case-id check weaker in the UI; refusal hidden behind CAPTURE_REASON_REQUIRED).** Fixed as Q-2. A missing reason
or case id stays 403 `CAPTURE_REASON_REQUIRED`; a case id that fails the shape or the identifier check is now 400
`CASE_ID_REFUSED`, ledgered `REFUSED_NO_REASON` with no reason and no case id (the stored row never holds the refused
value) and the message never repeats it. The UI checks the same shape (`caseIdAcceptable` in `api.ts`, the server's
digit-run join) before anything is sent, labels `CASE_ID_REFUSED`, and clears the field when the server refuses it.
Tests: `RedactedCaptureIntegrationTest.reasonsFollowTheRoleAndACaseIdCarriesNoIdentifier`,
`CaptureReasonCodesUiTest.aCaseIdIsAReferenceWithALetterAndNoIdentifier`, and two Vitest cases in `capture.test.tsx`.

**D-02 (browser persistence, state left after close, reader not self-guarding).** Decision: "autoComplete off,
spellCheck off, nothing persisted by the browser for case id and reason." Fixed: the form and the case-id field carry
`autocomplete="off"`, the field `spellcheck="false"` and no `name`; `close()` clears the reason and the case id;
`CaptureReader` renders nothing when `canReadCapture(me)` is false, and the form is valid only with a reason the user's
roles may give. Test: "keeps nothing for the browser to remember" (attributes, empty storage, cleared state).

**D-03 (count parsing).** Decision: "tighten the count parsing (digit boundaries, length, negatives) or better: add a
small structured `counts` object to the server health components (unmasked numbers only, no identifiers) and read that,
with a test on both sides." The structured object was chosen. `Views.ComponentView` has `counts` (sorted, fixed keys,
`long` values; empty for components without counts; the masked projection carries it unchanged since it holds no text).
`SiemExportService.Health` emits `<destination>.delivered`, `backlog` (only once counted), `queueDepth`,
`queueCapacity`, `stalled`, `heldBehindOpenTransaction`, `possiblyLostBatches`, `skippedAtStart`, `notStarted`, and
`readerFailure.<class>` / `senderFailure.<class>`; `CaptureHealth` emits `captureOn`, `keyAvailable`, `storeWritable`,
the skip counts by reason and, with the database up, the store totals and key states; the watermark emits `stale`,
`usedPerMille` and `skipped`. The UI no longer reads the detail sentence: `healthFacts.ts` reads `counts`, drops any value
that is not a non-negative safe integer, drops an empty destination, and ignores inherited keys. Server tests:
`SiemTransportTest` (refused and running exports) and `RedactedCaptureIntegrationTest` (watermark and key-state counts).
UI tests: `health.test.tsx`, including the malformed-value case. The active key id is no longer shown as a fact (a string,
not a count); it stays in the server's detail.

**D-04 (masked view of an incomplete notice).** Decision: "show the right message for an incomplete notice regardless of
the masked flag." Fixed: an incomplete notice shows "no text: the notice is incomplete" for every role; only a complete
notice is described as withheld from the masked view. Test: `notice.test.tsx` masked incomplete case.

## Merge with main (pull request 26)

After the merge of masking layers 4 and 5, the masked role's health details pass through the free-text masker
(`maskFreeText`); the counts are numbers and are carried unchanged in both projections, so the UI's facts are the same
for every role and never depend on the masked sentence. The leak probe now also asserts that every masked health
component carries `counts` with integral values under fixed-vocabulary keys. `IdentifierCheck` kept its semantics on
main (the estate comparison moved to `containsTerm`), so the case-id check is unchanged.
